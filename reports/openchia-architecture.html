Episode vs. CWL workflow

A CWL workflow describes a graph of deterministic process invocations whose shape is known before execution. An Episode describes a goal pursued by repeated attempts, where a registered numerical function decides at runtime how long to keep trying. CWL answers what runs, in what order, with which files. Episodes answer how do we know this is working, and when do we stop.

Four things CWL cannot express

  • A stopping rule under uncertainty. scatter is bounded iteration; when is a conditional. Neither is a value-of-information estimator. Loop constructs exist as engine extensions, but they are while-style control flow with no notion of diminishing returns.
  • Non-compositional credit. A parent recomputes progress on its own scale and does not sum child hypervolumes. CWL steps have no partial success to compose.
  • Attestation over reproduction. A model in the loop means re-execution will not match; OpenChia promises a hash-linked evidence chain instead. The second property cannot be retrofitted onto a standard built for the first.
  • Untrusted content as a type. ParentRequest/ChildResult are closed records so log text never becomes an upward instruction. In CWL, inter-step data is inert — the category does not exist.

Where CWL is clearly better

  • A standard with multiple independent engines (cwltool, Toil, Arvados, StreamFlow). OpenChia has one implementation.
  • A mature type system for scientific data — File with secondaryFiles, Directory, records. The Episode deliverable contract is thin by comparison.
  • A large corpus of existing tool descriptors; container and resource requirements as standard vocabulary.
  • CWLProv, and portability across established HPC and cloud schedulers.
  • It is declarative data, not emitted code — no planner, no emitter, no AST gate, no closure staging.

They compose — Episode as the adaptive outer loop, CWL as the deterministic inner tool

An Episode's unit invokes a CWL CommandLineTool or sub-workflow as a declared capability. CWL does reproducible, portable, containerized tool execution; the Episode observes the result, assigns credit, and decides whether another iteration is warranted. This also addresses a measured weakness: the registered-function catalog is presently a hand-edited 21-entry tuple in planner.py:322, and the seven *_library packages have no shared registry. CWL tool descriptors are a far better-specified substrate for “registered, validated, reusable component with typed arguments” than what exists today.

If a workflow is a static DAG of deterministic tools, CWL is the correct choice and the Episode model is overkill. The Episode machinery earns its complexity only where there is a genuine stopping decision to make under uncertainty. Recorded as docs/adr/0003-episode-workflows-are-not-cwl-workflows.md.
