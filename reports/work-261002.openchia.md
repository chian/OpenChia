## 1. What this system is

OpenChia is a fork of `NousResearch/hermes-agent` that adds a human–LLM *Duet* for
designing, materializing, running, and refining nested "Episode" workflows. The
inherited Hermes base supplies the terminal, provider, and state infrastructure;
OpenChia supplies the product.

The pipeline, and the authority boundary at each arrow:

```
human ⟷ conversational LLM
        → Duet                      LLM may propose; may not approve/build/run
        → Workflow Architecture     the authoritative design artifact
        → exact human /approve      binds one artifact id + content hash + authority head
        → EpisodeBuilder            consumes only the frozen approval, leaf-first
        → Materialized Specification
        → explicit human /run       separate command, full re-validation
        → isolated Episode tree     network-less, read-only, Landlock + seccomp
        → validated audit records
        → IterativeEpisodeRefiner   proposes a successor; cannot alter the baseline
        → exact human approval
```

The central claim is that **every state transition requires its own explicit human
command bound to an exact content hash**, and that no model — conversational,
planning, or in-Run — can cross a boundary on its own authority.

## 2. Is there a general design behind the app?

**Yes — and it is unusually coherent for a fork.** This is the most important
positive finding, and it should be stated before the defects, because it determines
how the defects should be treated.

The architecture is not prose over a stub. Independent review confirmed that the
load-bearing mechanisms are genuinely implemented:

- **The approval CAS is real.** `agent/duet_store.py:960-1054` performs state +
  authority-head + latest-artifact (id/hash/revision) checks plus a conditional
  `UPDATE` guarded by `rowcount != 1`, all inside `BEGIN IMMEDIATE`.
- **The frozen-workflow chain is re-verified on every read**, not trusted from
  cache (`agent/duet_service.py:468-644`); `verify_workflow_approval` re-derives
  the whole chain.
- **EpisodeBuilder structurally cannot approve its own output.** It receives a
  `BuildStore` and never a `DuetStore` (`episode_builder/service.py:319-330`);
  `grep commit_approval` across all three subsystems returns nothing.
- **Build → Run is a genuinely separate command** with full re-validation
  (`agent/openchia_host.py:1236-1283`).
- **Immutability is deep and deliberate** — `_freeze_json` → `MappingProxyType`,
  invariants asserted in `__post_init__` throughout.
- **Static admission is real**: 24 checks via `compile()` + AST inspection, without
  importing the generated package.
- **Run isolation is sound where it matters most**: closure staging is triple-verified
  (host, bootstrap, per-import re-hash); the source-only import finder is genuinely
  closed (verified by full AST closure); policy is applied *before* generated-module
  activation (`episode_runtime/worker.py:348-356`); terminal-ack phasing holds, and
  partial publication cannot become a successful receipt.
- **The best-designed seam in the codebase** is the model transport: a `ModelTransport`
  Protocol + ContextVar (`llm_call_library/transport.py:100-166`), correctly inverting
  the dependency on Hermes.

**The design is sound. The defects are implementation gaps against it, not a broken
concept.** That is a far better position than the inverse.

## 3. Critical findings

### C1 — No Episode that makes a model call can succeed **[verified by lead]**

**Severity: release blocker.** Reported by part 03; independently reproduced.

`protocol.py:_freeze_json` converts JSON arrays to **tuples**. `protocol.py:395`
freezes the model-request body on decode. `broker.py:77` requires
`isinstance(messages, list)`. `executor.py:1017` and `:1032` pass the frozen body
straight through. The resulting `ModelBrokerError` is caught at `executor.py:1124`,
which finalizes the Run `FAILED`.

Reproduction (identical payload, only list-vs-tuple differs):

```
after freeze, messages is: tuple
FROZEN (what the host actually gets): ModelBrokerError: model request needs one system and one user message
THAWED (control):                     ADMITTED ok -> task=episode_structured_json_fast
```

This is the **same defect class the project already patched** for INITIALIZE and
START (`protocol.py:264-266`, `:288-290` call `_thaw_json`). `_thaw_json` is applied
at exactly two sites and the model leg was missed. It survived because
`tests/episode_runtime/` has a full HTTP round-trip test but **nothing for the model
leg** — the single highest-value missing test in the repo.

Two further latent instances of the same class: `contracts.py:66` `_array`, and
`EpisodeEgressRule.from_record` (list-only).

**Fix:** thaw the model-request body at the executor boundary; add a round-trip test
for the model leg mirroring the existing HTTP one; audit all `from_record` entry
points for list-vs-sequence assumptions.

### C2 — `/approve` approves "whatever is current", not what the human read

**Severity: high.** Reported by part 01. Contradicts the project's central claim.

`OpenChiaHost.approve_current()` takes **zero arguments**
(`agent/openchia_host.py:521`) and `/approve` rejects any argument
(`openchia_cli/openchia_commands.py:309-312`). Meanwhile the LLM may still replace
the draft: `duet_service.py:781-787` accepts new drafts while in state
`AWAITING_WORKFLOW_APPROVAL`, and `duet_cli.py:655-662` dispatches slash commands
while a Duet turn is live.

The store-level CAS cannot catch this, because it compares *current against current*.
The race is above the store layer, where human intent is captured. This directly
contradicts `OPENCHIA_ARCHITECTURE.md:76` and `duet_owned_episode_design.md:170`
("the ones the human inspected").

**Fix:** mint an approval token (artifact id + content hash + revision) at workspace
render time; require `/approve` to carry it; reject on mismatch with a diff.

### C3 — The content-hash authority chain has no schema version

**Severity: high.** Reported by part 06.

No `schema_version`/`format_version` field exists anywhere in the OpenChia layer, and
`duet_store.py` sets `foreign_keys` and `journal_mode` but never `PRAGMA user_version`.
Because `_keys()` (`episode_contract_models.py:948`) enforces exact closed key sets,
adding one field makes every persisted Architecture unloadable **and** silently
rehashes identical designs — invalidating every prior human approval.

This is precisely the failure mode the authority model exists to prevent, and it is
currently unguarded. It also gates the schema work in C4.

### C4 — The four JSON Schemas were deleted and never replaced

**Severity: high.** Reported by part 06, confirmed by part 02.

Commit `5baa5a3b7d` removed `schemas/openchia/*.schema.json` (4 files), five
`docs/openchia/*.md`, and `GENERIC_NESTED_CREATORS_ARCHITECTURE.md` — including
`recursive_creator_threat_model.md`, the fork's only threat model. `schemas/` no
longer exists; `jsonschema` is not in `pyproject.toml`.

**Zero of six needed specs are machine-checkable** (Architecture format, Materialized
Specification, wire protocol, Run evidence, registered-function interface,
static-admission rule set). The Architecture "schema" survives only as a Python dict
(`episode_blueprints.py:473,539`) used *solely* as the LLM tool schema and never for
validation — and it has already drifted from the validators in four places.

### C5 — seccomp is allow-by-default with asymmetric architecture tables

**Severity: high.** Reported by part 03.

`seccomp.py:170` sets `"default_action": "allow"`. The aarch64 table (`:87-114`,
25 syscalls) omits `mknodat`, `mkdirat`, `truncate`, `ftruncate`, `fchmod`, `fchown`
that x86_64 (`:40-86`, 43 syscalls) denies — **and aarch64 is the default
macOS/Apple-Silicon container path**. Both omit `io_uring_setup` (the classic
denylist bypass), `memfd_create`, `open_by_handle_at`, the new mount API,
`unshare`/`setns`, and `process_vm_*`. No x32 guard.

There is a real gap between README's "seccomp applied by the worker" framing and a
hand-maintained denylist. Related: attestation validates the worker's seccomp hash
against the *host's* architecture.

### C6 — Authority-critical validation is implemented twice

**Severity: high.** Reported by part 02.

`agent/episode_blueprints.py:137-198` and `episode_builder/planner.py:357-437` are
independent implementations of function-selection admission — same five steps,
different role names, different error types. Drift means the Duet admits what the
Builder blocks, or worse, the reverse.

Compounding it: `content_id("approval", …)` and `content_id("workflow", …)` enumerate
the same 7 and 9 keys in **both** `agent/duet_service.py:162-184`/`:187-217` **and**
`episode_builder/_contract_chain.py:53-70`/`:72-94`. These hashes decide whether an
approval is authentic (`duet_service.py:448`). A field added to one site produces IDs
that stop agreeing across the Duet/Build store boundary.

## 4. Does it follow good design principles?

**Mixed, with a clear pattern: the value/store layer is excellent; the coordination
layer is not.**

**Strong:**
- Deep immutability and construction-time invariants throughout.
- Correct dependency inversion in two places: `ModelTransport` Protocol
  (`llm_call_library/transport.py`) and `RefinementAuthorityReader` Protocol.
- Genuine content-addressing and re-derivation rather than cached trust.
- Zero TODO/FIXME/HACK markers in the entire layer.

**Weak:**
- **God object.** `agent/openchia_host.py` is a 1,748-line class: 52 methods
  (23 public), 40 attributes, 12 responsibilities — three stores, two worker threads,
  an asyncio loop, the model transport, and CLI projection. `start_run` alone is 227
  lines. `build()` in episode_builder is 472 lines with 18 near-identical
  `_persist_receipt` branches.
- **Package cycles.** Four, including an `episode_builder → iterative_episode_refiner`
  layering inversion.
- **Misplaced ownership.** OpenChia contracts squat in `agent/`; six OpenChia files sit
  inside the 472-file inherited `openchia_cli/`.
- **Error reporting degrades the human's view.** `ContractDeficit.field_path` is a
  required non-empty dotted-lowercase string (`duet_contracts.py:30`), so
  document-level failures are anchored to the literal `"goal"` — a real editable
  field — at `:313`, `:324`, `:349`. The grammar cannot express `episodes[3].…`.
  `BuildDeficit` (`_contract_base.py:287`) has both a wider grammar and an
  `episode_local_id`: **the builder's deficit model is strictly better than the one
  the human actually reads.**
- **A real bug in that path:** deficit dedup keys on `(code, field_path, blocking)`
  but `ContractDeficit` has no episode field (`duet_service.py:406-409`), so three
  Episodes with bad deliverables collapse into one report naming whichever was last.

### The phantom catalog

`OPENCHIA_ARCHITECTURE.md:59-61` claims the host derives the function catalog from
registered libraries. It does not. The catalog is a **hand-edited 21-entry tuple
literal** at `episode_builder/planner.py:322-346`. Only four `FunctionLibrary`
instances exist, all in `numeric_control_library`, each holding one function; two of
them (`controller.py:314`, `credit_assignment.py:961`) are never queried at all. The
other libraries have no registry — just bare module constants.

**Adding a library function is silently invisible unless someone edits `planner.py`.**

This also explains the dead `EpisodeLibrary` methods: those registries were built for
a role they were never wired into. `LibraryFunction` is already the right shared
*definition* abstraction (5 of 6 use it correctly); what is missing is one layer up —
a shared registry plus a single catalog singleton. `episode_library/catalog.py:15-26`
is the one place that gets it right and should be the template. Any new shared module
must respect `_ALLOWED_IMPORT_ROOTS` (`admission.py:67`).

intermediate boolean rather than actual rejection for the `network` and `no-nnp` cases.

**The human-approval boundary is the product, and essentially nothing verifies it.**

## 8. Can the code be split into distinct parts?

**Yes. The answer is better than expected, and most of the work is already done.**

### UI/CLI ⟷ domain: splits cleanly

`agent/openchia_host.py:304-1877` already functions as a real facade: ~23 public
methods, each returning a JSON-safe dict or frozen dataclass. Both traced commands
confirm the seam:

```
/approve: keystroke → cli_tui_runtime_mixin.py:132 (or duet_cli.py:662)
        → OpenChiaCommandMixin.process_command (openchia_commands.py:386)
        → _handle_openchia_approve (:309)
        → OpenChiaHost.approve_current (openchia_host.py:521)
        → DuetService.approve_current_workflow
/run:    second dispatch table (openchia_commands.py:152) → start_run (openchia_host.py:1448)
```

Formatting happens only in the CLI. A grep for `print`/`rich`/`console`/`input`/ANSI/
`prompt_toolkit` across `openchia_host.py`, `duet_service.py`, `episode_builder/`,
`episode_runtime/`, and `iterative_episode_refiner/` returned **one hit** —
`container_executor.py:113`, inside an injected container script, a false positive.
One `logger.warning` total. Diff/baseline logic is correctly in the domain
(`iterative_episode_refiner/workspace.py:539-618`, `:1178-1259`); the UI only
prefix-matches to highlight.

**Blockers are small and specific:**
1. Domain imports the CLI: `openchia_host.py:95-98` → `openchia_cli.config`.
2. Run-executor backend policy lives in the CLI and derives the repo root from
   `duet_cli.py`'s `__file__` (`:200-207`).

### Creation ⟷ execution: the split already exists

`episode_builder/` and `episode_runtime/` are already distinct packages with a clean
handoff. **Not worth further splitting.**

### The real structural problem is placement, not coupling

Hermes coupling is **narrower than expected**: 12 import sites across ~40k LOC. The
entanglement is where files *live*, not what they import:

- Six OpenChia files sit inside the 472-file inherited `openchia_cli/`.
- OpenChia contracts squat in `agent/`.

**Top single cut:** move contracts to `openchia_contracts/`. This kills all four
package cycles and makes the lower ~33k LOC standalone.

### OpenChia is currently a *mode* of Hermes, not a product

Only 6 files / 4,349 LOC of 611 files / 247,936 LOC in `openchia_cli/` are
OpenChia-specific (**1.8%**). `openchia_main.py:67-88` blocks four flags, forces
`--cli`, and calls Hermes' `main()`. Confirmed empirically: `./openchia status` prints
"**Hermes Agent** Status". ~75 inherited subcommands are reachable and zero are
documented. `tui_gateway/` (40k), `ui-tui/` (67k), and `web/` (58k) contain **zero**
OpenChia references and are unreachable from `./openchia`.

### Proposed target layout

`openchia_domain/` + `openchia_ui/`, six new interfaces, seven ordered steps.
Estimated **1.5–2 engineer-weeks**, roughly half of it tests.

**Explicitly not worth splitting:** `episode_builder`/`episode_runtime` (already
split), the 605 inherited CLI files (merge-conflict risk against upstream — use an
entry-point allowlist instead), and the three dead UI trees.
