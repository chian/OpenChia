# Turn a requirement into a faithful assignment

Begin with the approved behavior and the target's role in its enclosing workflow.
Do not begin with a convenient file boundary, a list of activities or a generic
“improve quality” score.

## Build the requirement-to-evidence chain

For each assigned requirement, identify:

1. Its original requirement identity and authorized interpretation.
2. The exact candidate observation that establishes a gap, or the absent evidence
   that prevents an assessment.
3. A scoped change that could close that gap without dropping another requirement.
4. An independently grounded local predicate the coder can use while iterating.
5. The parent's acceptance condition, including the behavior local checks do not
   establish and the exact candidate/dependencies to which it will apply.

For example, “produce supported table rows” must distinguish a well-formed row,
correct source attribution, complete required identity, and supported field values.
Compiling the extractor or producing JSON establishes none of the latter by itself.

## Decompose only where the evidence can compose

RefineParts owns the division and selection of work. A nested Parts scope must
have a specific contribution and inherited preservation conditions. The union of
child task labels is not evidence that the parent's requirement has been met.

If A and B must hold together, declare that joint condition. Separate passes on
different revisions do not establish it. Numerical credit, rarefaction and
continuation are one coupled controller problem, even if they live in three files.
Design then implementation then acceptance are mandatory stages, not a menu of
unrelated sibling choices.

## Make a useful local metric without changing the goal

Prefer discrete, evidence-backed milestones tied to the behavior: correct unit
conversion on independently grounded cases, rejection of a forbidden transition,
or a newly satisfied joint condition. State preservation guards explicitly.

The parent supplies the local and acceptance contracts before coding. The host
admits them under the fixed policy. Count each semantic achievement only once;
splitting checks or renaming assignments cannot manufacture additional progress.
A milestone can support iteration without proving full parent acceptance.

## Stop unsupported interpretation early

Challenge the proposed contract with a trivial or wrong result that it should
reject. If it passes, refine the measure before the affected coding assignment.
Expected outputs cannot come solely from the current defective implementation.

When the task meaning is ambiguous, ask for the specific authorized interpretation
or return the unresolved decision. When the measure is inadequate, preserve the
failure and propose a successor assignment. Do not quietly weaken the active
criterion to make a favored implementation pass.
